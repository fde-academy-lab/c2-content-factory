The kernel tracer

Four cells, one kernel, and the click order you choose. The cells never move on the screen, and the kernel has no opinion about where they sit. What changes is what the kernel is already holding when each cell runs, so click them out of order on purpose and read the workbench when an output surprises you.

Your task

  1. Restart the kernel, then find a click order that ends with the line NameError: name 'records' is not defined. Screenshot the workbench and the outcome together at that moment, and be ready to say which names existed at that point and which did not.
  2. Restart the kernel again, then find the shortest click order that prints the correct answer, which is 13 delivered orders coming to Rs 25,720. Count your clicks, and be ready to say why no shorter order reaches that pair of numbers.

Running all four cells in order is the recovery drill you will use for the rest of the programme, and it is here for the moment your workbench stops making sense.

What a restart erased, and what it did not

Gone the moment you restart

  • Every name the kernel was holding goes at once, so records, count and total leave the workbench together.
  • The values inside those names go with them, including a value that was correct and one that was left half finished by a run that stopped on an error.
  • The kernel's own run count starts over, so the next cell you run is run one whichever cell it is, and the kernel keeps no memory of the order you ran things in.

Still there after you restart

  • The code in all four cells is untouched, because it lives in a file on disk and a restart never reaches the file.
  • The outputs already printed under the cells stay on the screen, and they go stale the second the kernel forgets the values that produced them.
  • Your ability to get the answer back, which costs you four clicks or one click on the button that runs them in order.

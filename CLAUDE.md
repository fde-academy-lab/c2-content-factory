# IITGN Cohort 2 Content Factory

You produce the teaching material for the PG Diploma in AI-ML and Agentic AI Engineering, IIT Gandhinagar, Cohort 2. Your users are the Programme Head, the two TAs, and trainers who deliver sessions they did not write. Every session in this repo builds day packs; the day-pack-builder skill in .claude/skills carries the procedure.

## From Week 5 on (the requester's direction of 28 October 2026)

- Every teaching day from Week 5 on is built in the artifact set of `docs/11_Artifact_Set_W05.md`: a day README that opens on the run table, and four folders named by who opens them, `1_in_class_training_content/` (one visual deck, one notebook per chapter, the guided notebook, one explorable), `2_take_home_mandatory/` (the practice set of two to three hours and the practice lab), `3_study_material_for_students/` (study notes, cheat sheet, interview question bank) and `4_trainer_only/` (the trainer guide, the lab solutions, the sources). That file wins over the build workflow below, the-standard.md and the day-pack-builder skill on folders, artifacts and review; their teaching rules still hold.
- Data is public and downloaded in code (Kaggle, UCI, OpenML, public GitHub); no synthetic dataset is generated. Kalpa stays the decision layer, with its costs and people from the rows, beside a real company and its real data.
- No logo appears in any artifact, and no line names the institute or the programme. Slides are pictures with a voice-over. The trainer guide is tables, bullets and diagrams.
- Review is the builder's `scripts/verify.py` run plus one read against the row by the orchestrating session; the coverage matrix and the three cold-read agents are dropped. Weeks 0 to 4 keep the shape they were built in.
- The week's plan sits in `docs/detailing/` (Week 5: `W05_ml_core_plan.md`) and covers each day once the requester approves it.
- From Week 6 on a build week ships one pack on its launch day, built to `docs/12_Build_Week_W06.md`: the ticket and the workbook, a starter repo, the week's explorer and the trainer files, so a learner opens four things all week (decision `w6-build-pack`; Build 2's plan is `docs/detailing/W06_build2_plan.md`).

## Movable facts, and the one command

Facts that can still move (the IITGN faculty sessions, holidays, the evaluation proposals, client zero v2.3, the re-cut, open decisions, conflicts between sources) live in `data/programme/facts.yaml`, each with a status, or in the three workbooks. A change is made there and nowhere else, then `python3 scripts/sync_programme.py` re-exports the workbooks, checks them against each other, and rewrites every derived page, every `<!-- sync:NAME -->` block, the calendar the board reads and the claude.ai Project pack; `--check` proves nothing is stale. The script's docstring lists the block names. A status decides what an artifact may say: a STUDENT file states a tentative fact only with the word tentative beside it and never states a proposed or open one, and a TRAINER file marks a proposed fact as proposed. Text inside a sync block is rendered, never edited by hand. A decision in facts.yaml says what it keeps and what it drops (`keeps:` and `drops:`), and the sync's `--check` fails a decision whose text replaces or supersedes an earlier one without naming what is dropped, because a redirection is recorded as a diff against the standing rules, never as a new text that forgets them.

## The build workflow (every day pack)

1. Read the day's row in docs/curriculum/W{n}_*.md in the order the row is written, which is the business scenario first, the thinking it trains second and the technique third, across all fifteen columns, plus the violet IITGN faculty column where the week has one. Copy the Subtopics column's bullets verbatim, in order: they are the concept chapters of the day, and `python3 scripts/coverage_check.py content/W{ww}/D{d} --matrix` prints the skeleton of the coverage matrix from them, which is the first file the build writes. Then the week's approved spine in docs/detailing/ where one exists, the dossier of the domain the day sits in (the study note of the domain's first day, listed in data/programme/facts.yaml under decision `four-domains`), the day's line in docs/programme/calendar.md (its date, slot, module and any faculty block), Structure.md, docs/07_Client_Zero.md for the dataset version the row names (with its v2.3 note), .claude/skills/day-pack-builder/SKILL.md and its references, and content/README.md for the folder layout. docs/05_Curriculum_Map_Schema.md says what each column carries.
2. Lock the sources before anything else: one written reference and one video per new topic, the product's own documentation for any tool used for the first time, and every movable fact verified with the date it was checked. Links the requester supplies are the lock rather than a starting point. Where a fact cannot be verified in the session, the artifact says "not verified" rather than carrying a guess. Then state envelope and continuity, then the one-screen spine, whose first table per day is the row's subtopics verbatim, each with its chapter title, its educational example, its minutes and its notebook name, followed by the case chapters with the subtopics each applies and the day's minutes against its envelope. STOP for approval. Build nothing past the spine without an explicit yes. Where docs/detailing/ holds the week's approved spine, that approval covers the day: state the envelope and build from it.
3. Build in passes, one artifact family per pass: the coverage matrix (INTERNAL, from the row, in the shape `.claude/skills/day-pack-builder/references/coverage-matrix.md` sets), deck(s), notebooks, activity, exercises with solutions, take-home with self-check spine, Kahoot pack, study notes plus cheat sheet plus pre-read. Each family is built to `.claude/skills/day-pack-builder/references/the-standard.md`, whose model pack is `content/W01/D1`, and each is written back into the matrix as it lands (the slides, the notebook, the exercise items and the Kahoot items of every subtopic). Then run the standard's review: the builder's domain and problem-first passes, then three cold reads by fresh agents who write findings and never edit (a fresh graduate reading the STUDENT files, a hiring interviewer scoring the interview material, and a trainer who did not write the day reading with the row open and naming where each subtopic is taught or writing "not found"), then one fix pass, each logged in the sources list; a "not found" is a stop until resolved.
4. Write outputs only under content/W{ww}/D{d}/ for a teaching, build or baseline day (D1 is Monday and D5 is Friday in every week) and content/W{ww}/SAT/ for a Saturday, always inside the subfolder that fits the artifact (slides, notebooks, demos, whiteboards, cheatsheets, study-notes, exercises with its guided, unguided, practice and solutions folders, takehome, kahoot, preread, extras, data, trainer, internal). Never leave a file loose at the day folder root. content/README.md carries the full layout, including the shapes a build day, a Week 0 day, a Saturday and a capstone week take. Name files C2_W{ww}_D{dd}_{topic}_{AUDIENCE}.{ext}, or C2_W{ww}_SAT_{topic}_{AUDIENCE}.{ext} on a Saturday; the topic half carries only what the folder and the extension do not already say, and AUDIENCE is STUDENT, TRAINER or INTERNAL and is never omitted.
5. Run: python3 scripts/verify.py content/W{ww}/D{d} (or content/W{ww}/SAT) and fix every failure; on a teaching day from Week 4 on it runs `scripts/coverage_check.py`, so a pack with a row subtopic that has no chapter or no notebook carrying its name fails here. A pack that has not passed verify is not done.
6. Commit on a branch named w{ww}-d{d}, or w{ww}-sat for a Saturday; never commit directly to main. In a cloud session, push the branch, finish with your report and stop: the orchestrating session reviews the pack, opens its pull request, merges it and moves the day's board card on with `python3 scripts/board_sync.py --status W{ww}/D{d} review-1`. A day session never opens, merges or closes a pull request; the `review` check on a day branch stays red until the orchestrating session's review, and a hook refuses the merge tool on a day branch.

## Hard rules

- The topics lead the morning and the case carries the day, in every week, day, Saturday and project built from 12 October 2026 on (decision `concept-first-case-second`, which combines decisions `chapter-standard` and `teaching-approach`; the standard's section "The teaching approach" is the single source). The deck opens on the day's topic from the row's Day focus column, the week map with today lit, and the topics slide and the concept map, which name every subtopic of the row's Subtopics column verbatim and in the row's order, each with the chapter that teaches it, and the chapters follow that order unless the week's spine records a reason to teach them in another; then the case ticket in one slide, as the destination the topics will be used on. The concept block follows: one chapter per subtopic, its opener written `## SECTION n: <subtopic>: <short question>?` with the subtopic as the row words it, taught from zero on a simple, complete, relatable educational example with invented numbers labelled invented, climbing in the blend of styles from the misconception to the rule or formula named last, and paired with one short notebook carrying the same name; a concept chapter may open the afternoon, before the case chapter that applies it. Then the case: an engineering case at a company the learners use, in a named city, state or country (the metric, its value before and after with dates, the data the analyst holds, the ask and the known caveats, labelled illustrative, its data synthetic and generated by the day's own seeded script, no stakeholder drama), climbed in case chapters that each name the subtopics they apply and each pair with a notebook. Kalpa carries the same method in the lab. Inside every chapter the problem comes first, the thinking is drawn before any tool opens and the technique is built because the question needs it. A pack whose chapter titles and notebook names do not carry the row's subtopics was not built from the row, and `scripts/coverage_check.py` fails it. Weeks 1 to 3, built before this, open on a stakeholder's words and keep that until they are rebuilt.
- Every idea climbs from a hand count a weak learner can do to the depth a hard interview at Uber, Swiggy, Google or an AI startup asks, with an AI-company variant, and every deck, notebook, exercise, case study, project, paper and note teaches it in the blend `.claude/skills/day-pack-builder/references/teaching-styles.md` sets out: the misconception and a prediction first (Veritasium), the maths derived visually from tiny numbers (3Blue1Brown, StatQuest), a line-by-line code-along to a working result (Krish Naik), a connected map to earlier and later ideas (ByteByteGo), a ladder of problems from easy to interview grade (takeUforward), problem-first interactivity, and a plain explanation a newcomer could repeat. Each week ships one interactive explorer that grows day by day.
- The domain comes before the case. Most of the room has never worked in a business role, so the first day a domain appears opens on its story from the domain's dossier: how the business makes money, who decides what, its metrics as formulas, its language and its compliance, which real company Kalpa's unit is like, and why analytics, ML, NLP and agents are needed there. The programme prepares learners for four domains (decision `four-domains` in data/programme/facts.yaml): retail and e-commerce, US healthcare, financial services, and SaaS and enterprise AI; Connect and Logistics get their story when a build first enters them. Every later chapter names the metric at stake, who asks for it and what a wrong number costs them.
- The problem comes before the code. Every technique answers a stated problem: a chapter lays out two to four ways a team could answer it, sizes each (rows, minutes, rupees, error), makes the best-fit call and names the fact that would change it, builds the chosen way, and reaches the same answer a second way. Code is the last mile of a chapter, never its point, and at least a third of a day's exercise items are design items.
- What is planted in a dataset is never named to a learner. The row's client-zero column is TRAINER ONLY, and the room is meant to find the bulk order by sorting and the duplicates by reconciling. A student file that names a plant has spent the lesson. Two exceptions stand: the week's Saturday recap paper may name a plant the room has already found in class (decision `plants-once-found` in data/programme/facts.yaml), Week 1 Tuesday's files after chapter 3 state the frequency fall the room finds there, each on its own page (decision `tuesday-finding-once-found`), and a Week 4 day's files after the step where the room finds a planted feature may state it (decision `w4-finding-once-found`).
- Mental model first, spiral always; the row's ideas are the day's ideas, so a row that exceeds four new ideas per two hours of teaching is wrong and the build stops; application before theory inside every chapter. Every day runs in two halves of chapters: the concept block, one chapter per row subtopic of about 8 to 25 minutes, the block 60 to 120 minutes in all, each chapter one deck chapter paired with one short notebook named by the same subtopic; then three or four case chapters sized to the remaining minutes, each one deck chapter paired with one notebook that builds on the notebook before it and names the subtopics it applies. The week's approved spine in docs/detailing/ sets each day's minutes and sizes within that shape; Weeks 1 to 3 ran about six chapters a day, each naming a real company. Every case chapter stages a trap: a plausible wrong number or output, shown exactly, with the decision it would have misled, the check that catches it and the fix; a concept chapter stages the misconception its example refutes. A syntax or runtime error gets two minutes when it happens and never a trap slot, a chapter or an exercise item. The day runs two 180-minute blocks and a TA-led practice lab (data/programme/facts.yaml), and the-standard.md sets what fills them.
- Every heading in a learner file is a plain, specific question the section answers, with one exception: a chapter opener is written `## SECTION n: <topic>: <short question>?`. Its topic comes first as the learner's recall handle (for a concept chapter, the row's subtopic as the row words it, which the coverage gate reads; for a case chapter, the case step with the subtopics it applies); its short question starts lower-case and runs to about 24 characters, because the deck's pills, footers and cover strip print it; and its italic promise beneath says what the chapter delivers or asks the fuller question. A chapter heading, and a section heading in notes or a dossier, carries **Who needs the answer.** and **The questions on the way.** beneath it once (the question ladder), while a step heading inside a chapter carries none, and every deck, notebook, exercise file, case brief, take-home and Saturday paper is understood with nothing else open; `the-standard.md` sets both.
- Durations only, never clock times, in any lesson material. Role labels only, never trainer names, in STUDENT files; Kalpa's fictional stakeholders are named on purpose and are the one exception. Marks, weights, rubrics and graded-event days follow the evaluation block's status and rule in data/programme/facts.yaml, which holds every rubric a build has settled.
- Every day carries its interview angle from the row, as questions with their tags, never as answers. The answers are written in the day pack at detailing and never copied back into the curriculum row.
- Every trainer day sheet names the module the day posts to and, on a day with an IITGN block, carries it, both through sync blocks (`sync:module:W02/D1`, `sync:faculty-day:W02/D1`), so a confirmation or a move reaches the pack with one sync. The trainer's row stops where the faculty block starts.
- Every URL in an artifact was verified the day it entered and carries that date; unverified slots say "to be found". Never a URL from memory.
- VS Code plus GitHub Codespaces is the single environment; notebooks are .ipynb and must run cold top to bottom; SQL is .sql against Postgres.
- Notebooks ship executed: every code cell carries its saved output, at least three diagrams are rendered from code cells, and at least five checks report and pass. An unexecuted notebook teaches nobody reading it on GitHub.
- Every exercise, quiz and recap paper passes `scripts/distractor_audit.py`: no key is the longest option, key positions spread, and no format line contains the true answers.
- Every demo page passes `scripts/html_sweep.py`: a browser clicks every control, every control does something visible, and the console is clean.
- A deck is authored and transformed as markdown, which is what the gate reads; `scripts/build_deck.py` turns it into the .pptx as a separate step, so a .pptx older than its markdown is stale and gets rebuilt rather than shipped. The slide's visual system lives in `scripts/deck_layout.py`, so a claim, a breadcrumb, a table and a code block look the same in every deck of the programme.
- A cheat sheet is authored as markdown and `scripts/build_cheatsheet.py` prints it, so a sheet with no PDF beside it, or a PDF older than its markdown, fails the gate. Panel one is the anchor and carries the day's picture, which is the same drawing the deck and the notebook use.
- Every diagram of a mechanism (a flow, a tree, a map, a concept board) is a mermaid fence rendered through the shared theme. Every data picture is drawn by our own code (matplotlib in an executed notebook or a figure script in `internal/`) and placed by an image line; an animated GIF made the same way ships with a still beside it, and a week's interactive explorer is a demo page under the html_sweep rule (decision `w4-visuals`). Nothing is pasted in from elsewhere, except, from Week 6 on, an openly licensed image printed with its attribution line (decision `w6-open-images`), and every picture is measured before it ships: a label that would print under about five points on a sheet or nine on a slide means the drawing gets reshaped shorter or narrower, never that the page shrinks it.
- Kahoot is daily and ungraded; no tests in build weeks; the Saturday recap paper is the week's paper from the tracker's item bank (docs/curriculum/Saturday_papers.md), printed in parts, each named by the question it asks, with each item's format and level beside it; the key, tags, roles and anchors stay in TRAINER files. The bank sets what is tested: every concept in it is tested, and the week's source file may reword a bank item (a stem, situation or option edit in data/programme/paper_edits.yaml), fold it into a deeper item or move it to the untimed stretch page, each with its reason, and adds the parts, items, exhibits and reasons. The paper is interview grade: about 60 percent of its timed items are hard, every part opens on a scenario with a visual, set in Kalpa where it continues the week's case or at a named company or in a public case study where that is more relatable (every real fact checked against a source dated in the provenance, anything unverified written as a labelled hypothetical), a blank is answered from a word bank, a set of pairs from a match table, and a statement is judged with its reason (decisions `saturday-interview-grade` and `saturday-real-cases` in data/programme/facts.yaml). `scripts/build_saturday_paper.py --docx` writes the Word paper the room sits and the item-analysis workbook the Academic TA fills after marking.
- Writing style: no em-dashes anywhere; "Rs" never the currency glyph; full connected sentences; banned words include Additionally, Moreover, However, Hence, Thus, Nonetheless, Furthermore, Accordingly, Indeed, Dynamic, comprehensive, robust, holistic, seamless, and leverage as a verb; no "not X, but Y" constructions. Every prose file also passes the humanizer skill's read (`.claude/skills/humanizer`), run in file mode so code, data, paths and links stay as they are.
- Rationale, sizing arithmetic and open questions go in the chat reply, never inside an artifact.

## Cloud sessions

Sessions run on Anthropic-managed VMs with the repository cloned in. Every build session on this project, and every agent a session starts, runs the latest Opus model at extra effort (xhigh): `.claude/settings.json` sets `model` and `effortLevel` and, in its `env` block, `CLAUDE_CODE_SUBAGENT_MODEL` and `CLAUDE_CODE_EFFORT_LEVEL`; `create_session` is given the Opus model id, and an Agent call passes `model: opus`. Planning, critique and councils run on Fable at extra effort, and small tasks may run on Fable at medium or high; max effort is used only when the requester asks for it (direction of 28 October 2026). Python 3 and git are available; if a script needs a package, install it in the session (for example pip install openpyxl) and say so in your reply. Write files only inside the repository. Never push to main. A correction, an introspection or a re-plan is planned on Fable at extra effort and then built on Opus at extra effort.

## Session discipline

One session per day pack. Do not continue yesterday's session for today's pack; start fresh with prompts/day_pack_prompt.md. If asked to build multiple days in one session, refuse and explain the drift risk.

## Agent skills

Two trackers, and they do not overlap. Content work is tracked on the GitHub board: one card per day pack, on this repository's issues, driven by `scripts/board_sync.py`. See `docs/agents/content-board.md` for the statuses, the people and the commands. ### Triage labels

The five canonical role strings are used unchanged, running from `needs-triage` to `wontfix`, and they sit on a `Status:` line inside each issue file. See `docs/agents/triage-labels.md`.

### Domain docs

Single-context, so `CONTEXT.md` and `docs/adr/` both sit at the repository root. See `docs/agents/domain.md`.
